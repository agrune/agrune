# Roadmap: agrune desktop-expansion research

## Overview

이 프로젝트는 현재 agrune의 browser-first 자동화 제품을 macOS 로컬 제어까지 확장할 수 있는지 판단하기 위한 연구 로드맵이다. 구현 자체가 아니라, 채널 인벤토리, 직접 어노테이션 방법 보고서, 어노테이션 대체 방법 보고서, 그리고 최종 제품 의사결정 패키지를 순서대로 만든다.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): planned milestone work
- Decimal phases (`2.1`, `2.2`): urgent insertions if research uncovers blocking surprises

- [x] **Phase 1: Channel Inventory and Constraints** - 현재 agrune 구조와 macOS/Chrome 제어 채널의 현실적 한계를 정리한다
- [x] **Phase 2: Annotation Methods Report** - 직접 어노테이션 방식 3가지를 비교하는 보고서를 만든다
- [x] **Phase 3: Annotation Alternatives Report** - 비-어노테이션 방식 3가지를 비교하는 보고서를 만든다
- [x] **Phase 4: Product Synthesis and Recommendation** - 6개 케이스를 종합 비교해 go/no-go 판단 자료를 만든다

## Phase Details

### Phase 1: Channel Inventory and Constraints
**Goal**: 현재 agrune의 browser-first 구조와 macOS 확장 후보 채널을 한 프레임 안에서 비교 가능한 상태로 만든다.
**Depends on**: Nothing
**Requirements**: [INV-01, INV-02, INV-03]
**Success Criteria** (what must be TRUE):
1. 현재 agrune의 브라우저 경로와 future desktop research seam 이 문서로 정리되어 있다.
2. `DOM/CDP`, `AX`, `Apple events`, `ScreenCapture`, `Vision`의 capability / prerequisite / permission 차이가 표로 정리되어 있다.
3. 일반 사용자 셋업 부담과 보안 리스크가 dated sources 기준으로 문서화되어 있다.
**Plans**: 3 plans

Plans:
- [ ] 01-01: 현재 agrune 브라우저 구조와 확장 seam 정리
- [ ] 01-02: macOS / Chrome control-channel capability matrix 작성
- [ ] 01-03: 권한, 보안, 사용자 셋업 제약 정리

### Phase 2: Annotation Methods Report
**Goal**: 앱이나 플랫폼 의미 정보에 기대는 직접 어노테이션 방식 3가지를 정의하고 비교한다.
**Depends on**: Phase 1
**Requirements**: [ANNO-01, ANNO-02, ANNO-03]
**Success Criteria** (what must be TRUE):
1. 직접 어노테이션 방식 3가지가 서로 materially different 하게 제시되어 있다.
2. 각 방식에 대해 앱 조건, 실행 모델, 실패 모드, coverage 가 정리되어 있다.
3. 각 방식이 browser / native / mixed 환경에서 어디까지 통하는지 confidence 와 함께 비교된다.
**Plans**: 2 plans

Plans:
- [ ] 02-01: 직접 어노테이션 3가지 케이스와 실행 모델 정의
- [ ] 02-02: 케이스별 평가 매트릭스와 coverage 비교 작성

### Phase 3: Annotation Alternatives Report
**Goal**: 직접 어노테이션이 불가능하거나 약한 경우를 위한 대체 방식 3가지를 정의하고 비교한다.
**Depends on**: Phase 2
**Requirements**: [ALTN-01, ALTN-02, ALTN-03]
**Success Criteria** (what must be TRUE):
1. 비-어노테이션 방식 3가지가 서로 materially different 하게 제시되어 있다.
2. 각 방식에 대해 타게팅, 검증, 복구, 로컬 ML 관여도가 정리되어 있다.
3. 각 방식에서 deterministic / probabilistic 경계가 명확히 문서화되어 있다.
**Plans**: 2 plans

Plans:
- [ ] 03-01: 대체 방식 3가지 케이스와 locator / recovery 모델 정의
- [ ] 03-02: 로컬 ML, 성능, UX, 안정성 평가 매트릭스 작성

### Phase 4: Product Synthesis and Recommendation
**Goal**: 연구 결과를 agrune의 실제 제품 방향 판단에 바로 사용할 수 있는 결정 패키지로 정리한다.
**Depends on**: Phase 3
**Requirements**: [SYN-01, SYN-02, SYN-03, SYN-04]
**Success Criteria** (what must be TRUE):
1. 6개 케이스가 동일한 평가 프레임으로 한 번에 비교된다.
2. 현재 agrune 구조를 기준으로 한 hybrid architecture 권고안이 제시된다.
3. 일반 사용자 대상 셋업/사용성 타당성과 첫 프로토타입 우선순위가 명시된다.
**Plans**: 2 plans

Plans:
- [ ] 04-01: 6개 케이스 비교 프레임과 의사결정 기준 통합
- [ ] 04-02: 권장 아키텍처, prototype order, go/no-go 제안서 작성
